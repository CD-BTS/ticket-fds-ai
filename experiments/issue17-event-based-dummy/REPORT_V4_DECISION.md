# v4 결과에 따른 BTS 적용 의사결정 정리 (Issue #17)

작성일 2026-11-24. [`REPORT_V4.md`](REPORT_V4.md) 와 `output/v4/` 의 저장된 결과, 그리고 현재 저장소의 서빙 코드를 읽어 정리했다.
**새 실험·모델 학습·서빙 코드 수정은 하지 않았다.** 수치는 모두 기존 결과 파일에서 가져왔다.

> 모든 성능 수치는 합성 데이터 안의 값이다. 실제 사용자에 대한 성능이 아니다.
> "권장" 은 "합성 데이터의 여러 생성 가정에서 일관되게 나았다" 는 뜻이고, 운영 성능을 보장하지 않는다.

## 결론

| 구분 | 내용 |
|---|---|
| **확정할 수 있는 것** | (1) Feature 6개의 종류와 계산식은 실험과 BTS 백엔드(`ticket-fds-admin/backend`)가 같다. (2) 6개 중 바꿀 근거가 나온 것은 `booking_interval_variance` 하나다: 간격이 5개 미만이면 null. (3) 세션 기준 간격은 지금 모델 구성에서는 적용하지 않는다. (4) 나머지 5개 Feature 는 그대로 둔다 |
| **실험과 서빙이 다른 것** (먼저 맞춰야 한다) | 실험의 모델은 "결측 중앙값 대체 + log1p, contamination auto, 임계값은 validation 오탐률 5%" 다. 저장소의 서빙 번들 스크립트(`pack_bundle.py`)는 "전처리 없음, contamination 0.20, 원본 더미로 학습, 정규화 점수 0.5" 다. **실험 결과는 지금의 서빙 번들에 대한 것이 아니다** (0절) |
| **아직 결정할 수 없는 것** | 최소 간격 수 5 라는 값, 임계값의 실제 수준, 실제 오탐률·탐지율, 세션 기준의 장기적 채택 여부, IP·카드 Feature 의 실제 기여 |

## 1. Feature 6개의 현재 정의와 권장 정의

| Feature | 현재 정의 (BTS) | 권장 | 근거 |
|---|---|---|---|
| `avg_booking_interval` | 30일 창에서 연속한 두 시도의 시작 시각 차이의 평균(초). 시도 2건 미만이면 null | **유지** | 세션 기준·중앙값·종료→시작 후보가 혼합 학습에서 일관되게 낮거나 차이가 없었다 |

## 2. 변경 전후 계산식과 이유

`intervals[i] = max(0, start[i+1] − start[i])` (초), `n = bookingCount − 1` (간격 수).

| | 변경 전 | 변경 후 |
|---|---|---|
| `avg_booking_interval` | `n ≥ 1` 이면 `mean(intervals)`, 아니면 null | 같음 |
| `booking_interval_variance` | `n ≥ 1` 이면 `Σ(x − mean)² / n`, 아니면 null | **`n ≥ 5` 이면 `Σ(x − mean)² / n`, 아니면 null** |
| 나머지 4개 | | 같음 |

**이유**

1. 지금 정의에서는 시도가 2건인 계정의 분산이 식으로 0 이 나온다. v4 에서 1,000계정 중 152계정(D1·D2) ~ 155계정(D3)이 그렇고 대부분 정상 계정이다.
2. 간격이 2~4개여도 분산은 작게 나온다. 실측한 정상 사용자 1명의 계정 중 간격이 2개인 계정의 분산은 0.02, 0.06초² 로 매크로(0.06~0.22초²)보다 작았다.
3. 그 결과 "분산이 작다" 가 정상 계정에 흔한 값이 되어, 분산이 작은 반복 매크로가 드문 값으로 보이지 않는다.
4. 간격이 5개 미만인 계정의 분산을 null 로 두면 작은 분산이 반복 시도를 한 계정에만 남는다.
5. 기존 Credit 규칙의 "분산 1.0 미만 **이고 시도 5건 이상**" 과 같은 생각이다.

- 1~4번은 결과에 맞는 설명이지만 **따로 검증한 것은 아니다** (원인을 분리하는 실험은 하지 않았다).
- 변경 후 분산이 null 인 계정: 정상 81%, 이상 37% (D2). 분산이 "시도가 많은 계정에만 있는 값" 이 된다.

## 3. 최소 간격 5개 조건과 미충족 시 처리

| 항목 | 내용 |
|---|---|
| 조건 | 30일 창의 간격 수 `n = bookingCount − 1` 이 5 이상 (= 시도 6건 이상) |
| 미충족 시 (백엔드) | `bookingIntervalVariance = null`. 0 이나 다른 값으로 채우지 않는다. `avgBookingInterval` 은 지금처럼 `n ≥ 1` 이면 계산 |
| 미충족 시 (AI 서버) | null 을 **학습 데이터의 중앙값으로 대체**한 뒤 log1p. 실험이 이 방식이다. 지금의 번들에는 대체 단계가 없으므로 번들에 전처리를 넣어야 한다 (0.2절 1번) |
| 요청 검증 | `bookingIntervalVariance` 는 이미 null 허용이라 스키마 변경이 없다 |
| 판정 불가 처리 | 분산이 null 이어도 점수는 낸다 (`INSUFFICIENT_DATA` 가 아니다) |

**주의**

- 5 라는 값은 사전에 정한 후보 하나다 ("없음 / 5개" 두 가지만 비교했다). 3 이나 10 이 더 나은지는 모른다.
- 조건을 "간격 5개" 로 할지 "시도 5건"(Credit 규칙의 표현, 간격 4개)으로 할지에 따라 1건 차이가 난다. 실험은 **간격 5개**다.
- 대체값(중앙값)은 간격이 5개 이상인 계정에서만 계산된다. 이 계정들은 시도가 많은 쪽이라 중앙값이 전체를 대표하지 않는다. 실험에서는 이 방식으로 결과가 좋았지만, 실제 데이터에서 대체값이 어디에 놓이는지는 확인이 필요하다.

- 권장 정의의 최악은 "모든 계정이 오픈 1회에만 참여하고 정상 사용자가 빠른" 조건이다. 이때도 현재 정의(0.566)보다 0.12 높지만 seed 에 따른 흔들림이 크다 (0.10).

- **이 66개 결과는 독립적인 검증이 아니다.** 권장 정의는 test 결과를 보고 고른 것이고, 사후 확인도 같은 합성 생성기의 데이터다.

## 5. 권장 모델 설정

실험에서 쓴 구성이다. 실험은 이 구성 하나만 평가했고 다른 설정과 비교하지 않았다 (추가 튜닝 없음).

| 항목 | 권장 (실험 구성) | 현재 서빙 번들 스크립트 | 결정 가능 여부 |
|---|---|---|---|
| 모델 | `IsolationForest(n_estimators=100, contamination="auto")` | `n_estimators=100, contamination=0.20` | 가능. 점수만 쓰면 contamination 은 무관하다 |
| 전처리 | 결측 중앙값 대체 (train 에만 fit) → log1p (`avg_booking_interval`, `booking_interval_variance`, `booking_count`). 스케일링 없음 | 없음 | **가능: 번들에 전처리를 넣어야 한다.** `REPORT_V2_TUNING.md` 에서 "결측 그대로" 보다 높았고 v4 는 이 전처리로만 평가했다 |
| 최소 데이터 기준 | 시도 1건 이상이면 점수 산출 | `min_booking_count=1` | 가능 (같음) |
| 학습 데이터 | 혼합 (레이블로 고르지 않은 전체 계정) | 원본 더미 | 조건부. 아래 |
| 임계값 | validation 정상 계정의 오탐률 ≤ 5% 가 되는 가장 낮은 점수 | 정규화 점수 0.5 | **방식은 가능, 값은 불가.** 아래 |

**학습 데이터 구성**

| 구성 | 권장 정의에서 | 판단 |
|---|---|---|
| 혼합 | F1 0.766~0.778 (세 가정) | **기본.** 레이블이 필요 없고 30일 정의에서 가장 고르다 |
| Credit 규칙 통과 계정만 | 현재 정의에서 0.712 / 0.702 / 0.700 (혼합 0.717 / 0.702 / 0.709 와 같음). 권장 정의에서는 평가하지 않았다 | 30일 정의에서는 이득이 없다 |
| 정상만 (레이블 필요) | 현재 정의에서 0.743 / 0.733 / 0.733. 권장 정의에서는 평가하지 않았다 | 운영에서는 레이블이 없어 쓸 수 없다. 상한 참고용 |

- 권장 정의 × Credit 통과 / 정상만 조합은 실험에 없다. 혼합 학습에 대해서만 말할 수 있다.
- 실제 학습 데이터는 운영 이벤트여야 한다. 합성 데이터로 학습한 모델을 운영에 쓰는 것은 이 실험이 지지하지 않는다.

**임계값**

- 방식(정상으로 볼 수 있는 계정의 오탐률을 목표로 임계값을 정한다)은 권장할 수 있다.
- 값은 정할 수 없다. 실험의 임계값은 합성 데이터의 점수 분포에서 나온 것이고, 운영에는 "정상" 레이블이 없다.
- 지금의 `anomaly_threshold=0.5`(백분위 점수)는 학습 사용자의 절반이 넘는 점수라는 뜻이다. 실험의 기준(정상의 5%)과 다르다. 백분위 점수를 유지한다면 0.95 근처가 실험의 기준에 대응하지만, 이상 계정이 섞인 학습 데이터의 백분위와 정상 계정의 오탐률은 같지 않다.

## 7. 모델이 쓰는 Feature 와 IP·카드 탐지 효과의 관계

Ablation 은 하지 않았으므로 Feature 별 기여를 수치로 나눌 수는 없다. 저장된 결과에서 읽을 수 있는 것만 적는다.

**모델 입력**: 6개 전부다. IP(`ip_booking_density`)와 카드(`card_reuse_count`)는 별도 규칙이 아니라 모델의 입력 2개다.

| 관찰 (현재 정의, 혼합 학습, 탐지 비율 D1 / D2 / D3) | 값 |
|---|---|
| 이상 계정: 같은 IP 의 계정 수 5 이상 | **1.00 / 1.00 / 1.00** |
| 이상 계정: 같은 IP 의 계정 수 2~4 | 0.59~0.63 / 0.54~0.63 / 0.53~0.63 |
| 이상 계정: 같은 IP 의 계정 수 1 | 0.49 / 0.46 / 0.47 |
| `multi_account` (IP 5~11계정, 카드 공유) | 0.994 |
| 단독 `fast` / `jitter` | 0.35~0.40 / 0.39~0.42 |
| human 프로필 매크로 (모두 `multi_account` 링 안) | 1.00 |
| 정상 계정: 같은 IP 의 계정 수 5 이상 | 오탐 **0.25 / 0.21 / 0.18** |
| 정상 계정: 같은 IP 의 계정 수 3~4 | 오탐 0.12 / 0.14 / 0.13 |
| 정상 계정: 같은 IP 의 계정 수 1~2 | 오탐 0.02~0.03 |
| `shared_ip` 정상 사용자 | 오탐 0.16~0.20 |
| 단일 Feature AUC: 카드 / IP (전체 이상) | 0.678 / 0.648 |
| 단일 Feature AUC: 카드 / IP (매크로만) | 0.748 / 0.732 |

- **탐지의 상당 부분이 IP·카드 공유에서 나온다.** 공유가 큰 계정은 100% 잡히고, 공유가 없는 매크로는 절반 이하만 잡힌다.
- **오탐도 같은 Feature 에서 나온다.** 같은 IP 를 5계정 이상이 쓰는 정상 사용자의 18~25% 가 탐지된다.
- "사람처럼 느린 매크로를 잡는다" 는 결과(human 프로필 Recall 1.0)는 간격 Feature 의 효과가 아니다. 그 계정들이 IP·카드를 공유하기 때문이다.
- 권장 정의는 IP·카드와 무관한 쪽(단독 fast·jitter, `hold_cancel`)의 Recall 을 올린다. IP·카드 쪽 결과(`multi_account` 0.994, `shared_ip` 오탐)는 거의 그대로다.
- **합성 데이터의 IP·카드 공유는 v2 에서 물려받은 가정이다** (다계정 링 5~11계정, 정상 공유 IP 4~6계정). 실측은 없다. 실측 환경에서는 모든 계정이 같은 IP 와 결제수단 3개를 써서 이 두 Feature 가 계정 수(9, 8)로 나왔다. 실제 서비스에서 NAT·공용망·기업망이 얼마나 흔한지에 따라 오탐이 크게 달라질 수 있다.

## 확정 사항과 미결정 사항

**실험 결과로 확정할 수 있는 것**

1. Feature 6개의 종류는 유지한다. 실험과 BTS 백엔드(`ticket-fds-admin`)의 계산식은 같다.
2. 변경할 Feature 는 `booking_interval_variance` 하나이고, 변경 내용은 "간격이 5개 미만이면 null" 이다. (합성 데이터의 모든 가정·조건에서 현재 정의 이상이었다는 범위에서)
3. 세션 기준 간격, 중앙값, 종료→시작 간격은 지금의 모델 구성(혼합 학습 Isolation Forest)에는 적용하지 않는다.
4. 모델 번들에는 결측 중앙값 대체와 log1p 가 들어가야 한다. 지금의 번들 스크립트는 실험 구성과 다르다.
5. Feature 정의 변경과 모델 재학습·번들 재생성은 함께 배포한다.
6. 임계값은 고정된 0.5 가 아니라 목표 오탐률에서 정한다 (방식).

**아직 결정할 수 없는 것**

1. 최소 간격 수의 값 (5 인지, "시도 5건" 인지).
2. 임계값의 실제 수준과 그때의 오탐률·탐지율.
3. 권장 정의가 운영 데이터에서도 이득인지 (합성 데이터의 "시도 2건인 정상 계정이 많다" 는 구조에 기대고 있다).
4. 학습 데이터에서 이상 의심 계정을 덜어낼지 (권장 정의와의 조합은 평가하지 않았다).
5. 세션 기준 간격의 장기적 채택 (정상 사용자의 속도 분포와 대기열 대기 시간을 알아야 한다).
6. IP·카드 Feature 를 지금처럼 쓸지 (공유 IP 정상 사용자의 오탐 15~22% 가 실제로도 그런지 모른다).
7. 단독으로 움직이는 fast·jitter 매크로(절반가량 미탐)와 느린 단독 매크로에 대한 대응.
8. 배포 대상 백엔드와 번들이 무엇인지 (저장소만으로는 확인되지 않는다).
