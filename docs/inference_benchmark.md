# Isolation Forest 추론 방식 성능 측정

## 측정 방법

```powershell
python scripts/benchmark_inference.py --iterations 100 --warmup 10 --output benchmark.json
```

- 모델 학습과 첫 호출 워밍업은 측정에서 제외합니다.
- `batch_size=1`은 `assess` 단건 호출을 반복합니다.
- `batch_size=10/50/100`은 동일한 payload를 `assess_batch`로 한 번에 처리합니다.
- latency는 한 호출 단위의 p50/p95/p99이며, throughput은 처리한 사용자 수/초입니다.
- 기본 데이터와 random seed가 고정되어 실행 간 비교가 가능합니다. 실제 운영 결과는
  CPU, Python/scikit-learn 버전, payload 크기, 동시 요청 수에 따라 달라질 수 있습니다.

## 실행 주기 결정 기준

실제 트래픽에서 측정한 p95 latency가 FDS 골든타임의 20% 이내이고, 예상 peak 유입량보다
높은 throughput을 보장하는 방식을 선택합니다. 배치 대기 시간이 골든타임을 초과하면
throughput이 더 높더라도 해당 배치 크기를 사용하지 않습니다.

## 측정 예시

현재 개발 환경에서 100회 반복(`--warmup 10`)한 결과는 다음과 같습니다.

| 방식 | p50 (ms) | p95 (ms) | p99 (ms) | 처리량 (건/초) |
|---|---:|---:|---:|---:|
| 단건 순차 | 30.031 | 54.966 | 63.039 | 30.00 |
| 10건 배치 | 40.261 | 70.802 | 102.472 | 226.73 |
| 50건 배치 | 84.228 | 117.367 | 166.067 | 560.65 |
| 100건 배치 | 148.500 | 191.698 | 231.805 | 652.62 |

이 측정에서는 10건 배치가 단건 대비 처리량을 약 7.6배 높이면서 p95 latency를
약 71ms로 유지했습니다. 다만 이 결과는 개발 환경의 참고값이며, 운영 확정 전에는
peak 트래픽과 실제 골든타임을 대입해 재측정해야 합니다.

초기 연동은 `POST /predict/batch`를 사용하는 10건 마이크로 배치로 시작합니다. 10건
배치가 peak throughput을 충족하지 못하면 50건, 100건 순서로 확대하고, 어떤 배치도
골든타임과 peak 부하를 동시에 충족하지 못하면 동기 단건 호출 대신 비동기 큐로
분리합니다. 최종 수치는 운영과 유사한 환경에서 위 명령을 실행한 결과로 갱신해야 합니다.
